# Argument Arena user and operator policy

The six README phases are implemented in the existing Python bot. Start with [installation](getting-started.md), then `/setup`. [Commands](commands.md) lists the executable surface. [Feature coverage](feature-checklist.md) connects every README section to code, tests and documentation. Live installation and provider quality evaluation remain operator work; offline validation makes no deployment claim.

## Setup and negotiation

`/setup` requires Administrator and selects four categories, optional announcement/results channels and a moderator role. `/settings server` displays the complete configuration; its optional `patch` JSON updates it with an execution-time Administrator check. `/settings audit` records server changes. Moderator roles can control matches and review results, but cannot configure server authority or credentials.

Server defaults are materialized from `settings.py`. Initial limits are three open matches per member, a 60-second challenge cooldown, 100 research operations per UTC day, 200 LLM requests per UTC day and 100 LLM requests per match. A request has a bounded input and at most 3,000 completion tokens. These are request ceilings, not a dollar estimate; set lower limits for expensive models. Retries consume usage because an uncertain provider request may have been billed. Daily usage resets by UTC day; per-match allowances are lifetime totals. Source fetches are bounded by research depth plus up to five dispute links. Training shares the daily LLM allowance. No account or subscription is created by the bot.

`channel_name` defaults to `match-{id}`. `match_prefix` optionally prefixes random 12-hex-digit IDs with up to 12 lowercase letters, digits or hyphens. Category IDs, output channel IDs and moderator role IDs in JSON are **strings**. The active category is required before challenging. Other absent routes leave the closed channel in its current category, with posting locked. Private credentials never belong in server JSON.

Example server patch:

```json
{
  "max_concurrent": 2,
  "defaults": {"inactivity": {"hours": 48}},
  "presets": {"practice": {"coaching": {"enabled": true}}},
  "llm_models": {"analyze": "default", "research": "default", "training": "default", "battle": "default"}
}
```

`default` uses server defaults. Built-in presets are `casual`, `ranked`, `research-off` and `coaching`; custom presets are validated independently against the starting settings. Changing a server default does not rewrite an existing proposal or accepted match. Topic and both positions are chosen explicitly. Neither a thread's participants nor its topic are silently adopted as personal beliefs.

A challenge records its channel/thread origin link. `/match settings` displays every effective parameter, positions and revision. Its feature selector exposes **ON/OFF**, a toggle and a JSON parameter form for all 20 features. The same command accepts a JSON patch and an optional two-position JSON array. Every change clears confirmations and increments the revision. Both participants must confirm that exact revision using the button or `/match accept match_id:… revision:…`. Stale buttons cannot accept changed rules. Pending challenges expire after seven days. Accepted competitive settings are immutable; use a new challenge to negotiate different rules. Staff interventions concern lifecycle/results and are audited.

## Every match feature

The following names are the keys accepted by `/match settings patch`. Every object includes `enabled: true|false`. Parameters below are starting defaults; changes are visible in the effective configuration. Integers are bounded, lists contain at most 25 strings, and research depth is 1–10. The JSON configuration and UI use the same validator.

| Feature key | Starting switch | Parameters and behavior |
| --- | --- | --- |
| `claims` | On | `every: 1`, `detail: "full"` or `"summary"`; publication frequency per accepted message. `/match claims` exposes the attributed graph/history only when public tracking is on. Internal extraction can still support research/judging. |
| `research` | On | `depth: 3`, `sources: []` preferred source hostnames, `budget: 20` total research operations per match. Search results are inspected as HTTPS pages. Preferences prioritize results without discarding contrary evidence. |
| `corrections` | On | `confidence: 0.85`, `delivery: "batched"` or `"immediate"`. Contradicted/partly supported checks above threshold produce sourced flags; batched delivery waits 60 seconds. Requires background research; disabling it turns corrections off. |
| `on_demand` | On | `limit: 10`, `depth: 3`. Independent of background research and subject to the shared research budget. Duplicate pending checks do not spend another request. Disputes can queue rechecks. |
| `fallacies` | Off | `families: []` includes all supported model labels, `every: 3`. Nonempty families filter exact case-insensitive labels. Every finding requires a quoted passage and explanation. |
| `coaching` | Off | `delivery: "private"` or `"public"`, `every: 3`. Private means a DM; a blocked DM becomes a failed delivery, without public fallback. |
| `civility` | On | `strictness: "normal"` (`"gentle"`, `"strict"`), `escalation: "notify_staff"` or `"remind"`. No automatic sanctions; escalation creates an audit event and notification in the announcement channel when configured. Server rules still apply when feedback is off. |
| `live_scores` | Off | `every: 5`; provisional rubric scores, clearly separate from final results. They wait for currently queued claim/research work. |
| `judging` | On | `rubric: "arena-v1"`, six `weights`, `model: "default"`, `tie_threshold: 3.0`, `tie_policy: "draw"` or `"inconclusive"`. Disabling judging also disables ranked status. |
| `feedback` | On | `detail: "full"` or `"summary"`, `delivery: "public"` or `"private"`. Actionable strengths, needs, unanswered objections and practice references. Also works without final judging and after procedural endings, without changing the outcome. |
| `turns` | On | `first: 0` (or `1`), `structure: "message"` or `"submit"`. A substantive nonempty text message advances automatically in message mode. Submit mode allows multiple messages before `/match submit`. Out-of-turn messages are visibly excluded. |
| `inactivity` | On | `hours: 24`; starts when a member is designated as owing a response. Flexible-order matches require a mutually agreed `/match request`. Only that member's qualifying response clears the requested clock. |
| `reminders` | On | `before_hours: 2`, `delivery: "channel"` or `"private"`. Lead time must be shorter than an enabled response window. Reminders do not reset a clock. |
| `limits` | Off | `rounds: 10`, `messages: 100`, `characters: 4000`. A round is two completed turns. Message/round caps finish the debate; overlength messages are excluded with an explanation and may be resubmitted. |
| `reactions` | On | `allowed: []` allows all emoji; a nonempty list is an exact emoji allowlist. Disallowed reactions are removed. Reactions never enter the transcript. |
| `threads` | On | `create: true`, `close_after: false`. Public threads allow discussion independently of main-channel posting. `close_after` closes thread participation on match closure. |
| `audience` | Off | `hours: 24`, `eligibility: "spectators"` or `"members"`. One replaceable vote per eligible human after closure. The vote is displayed separately and never affects scores or Elo. |
| `ranked` | Off | `preset: "ranked-v1"`. Requires the fixed competitive judging/turn/deadline/limit rules described below. |
| `profiles` | On | Each member must also explicitly enable their own analysis. Applies only to consented managed matches, with timestamps and removal protection. |
| `archive` | On | `lock_threads: false`. Automatically moves to the outcome route and locks main-channel participant posting. Thread locking also applies when `threads.close_after` is enabled. Main-channel posting locks even when movement is off. |

Publication frequencies count accepted messages rather than bot, spectator or thread messages. Large configuration/report/evidence responses arrive as ephemeral JSON attachments so nothing is silently truncated. Ordinary slash responses are ephemeral; only durable bot notices post publicly. Settings forms expire after five minutes; slash commands continue working across restarts.

## Channels and durable lifecycle

Channels are public. Explicit overwrites deny ordinary main-channel posting for **every nonstaff role**, then permit the two participants, configured moderators and bot. This handles Discord's role-allow precedence. Ordinary roles also lose channel/webhook/message/thread management inside a match, so those permissions cannot be used to bypass posting policy; configured staff and Administrator retain moderation authority. Spectators retain application commands, enabled reactions and separate public thread permissions. Administrator retains Discord's permission bypass. Threads/reactions/staff chatter are excluded from the official transcript. Text from accepted participant messages is the official input; attachments must be submitted as evidence URLs through a dispute. Accepted rules also apply during recovery. A role added later and changes to moderator roles queue permission reconciliation.

Pause/resume, extensions, draws, finish and cancellation require the peer's identical proposal or staff action. A proposal does not change the clock. A pause saves remaining seconds, resume restores them, and extensions add 1–168 hours. Concession is immediate. `/match status` includes exact UTC deadlines, proposal state and pending/failed jobs. Posting locks during pauses and judging. Finishing/limits enter judging, or record an inconclusive result when judging is off. Concessions, draws, inactivity forfeits and cancellations retain their distinct outcome types.

The worker evaluates clocks every 15 seconds. Only a designated required response changes a deadline; other activity never extends it. Clock updates, closures, results and ratings are transactional. Duplicate events and racing finish/forfeit requests cannot apply results twice. Scheduled jobs use unique IDs, leases, bounded retries and explicit errors. Dependency waits do not exhaust provider retries. A failed provider does not invent a winner: judging stays pending until retry or a documented staff correction/cancellation.

Before checking an overdue response, the worker compensates the entire unobserved interval when disconnected, restarting, or more than 60 seconds have elapsed since its last clock observation. It reconciles channel history before enabling forfeits. Failed reconciliation keeps deadline enforcement suspended. This deliberately favors extra time over an unfair loss. A fresh speaker designation after recovery gets a fresh window. Recovered edits/deletes do not retroactively change clocks. Completed match channels are checked for missed revisions too. A deleted/unavailable match channel pauses its response clock for staff resolution. The polling interval can provide a small additional grace period before closure.

Message revisions and deletion markers are durable. Old claims/checks become stale; changed wording receives new claim IDs. Delayed correction flags are suppressed when the underlying claim or check was superseded. An edit/delete or changed researched verdict after completion marks an affected judgment for staff review, withdraws its ratings through deterministic replay, and removes stale generated profile observations. `/match correct` requires staff, an explicit outcome/winner and review explanation. It retains the old outcome in audit history, replays all affected later ratings and reroutes archival. If the transcript changed, the obsolete report is removed on review. `/match retry` retries failed jobs after fixing configuration or waiting for a daily budget reset. Staff can cancel an unresolved judging match or use `/match close` to record an explicit reviewed outcome without inventing a provider response. A failed judging job never assigns a procedural loss.

Channel creation uses an immutable topic marker to recover an uncertain successful Discord create. Notice deliveries use per-part markers and durable acknowledgements, recovering a send that succeeded before a process crash. Moves always use explicit overwrites and `sync_permissions=False`; closure never imports a category's broader posting permissions. Closed threads follow the accepted policy. No automatic channel deletion is performed.

## Research and model boundaries

OpenAI-compatible Chat Completions is the real JSON LLM integration, with an operator-configured model and endpoint. Brave Web Search plus bounded HTTPS page retrieval is the real research integration. Runtime files supply keys; absent/invalid credentials report `not_configured`/`credential_unavailable`. Provider failures, rate limits, budget exhaustion, unsupported pages and oversized inputs remain visible job/check states. `/match status`, `/match claims`, `/train current` and retry commands expose them. No paid calls run in CI.

Claims retain exact attributed quotes, labelled summaries, kind, original message URL/time, author and revision. IDs contain message/revision/index. Only factual claims are researched automatically. Values, opinions, definitions, predictions and questions retain their own types. Relations link support, rebuttal, response, concession, revision and objection within the same match. An unanswered objection is not automatically a concession. Ambiguity produces clarification instead of silently changing the quotation.

Each completed check includes explicit verdict, confidence, explanation, source IDs, actual fetched URLs, title, publication date when available, last-modified metadata, retrieval timestamp, content hash and provenance. Unknown publication dates remain unknown. Search snippets alone and model recollection never become evidence. Empty retrieval produces **insufficient evidence**. Submitted source links are fetched with the same controls and clearly marked participant-provided. Disputes preserve prior verdicts and append rechecks/corrections. A clear sourced contradiction can flag an incorrect statement without making moral preferences factual.

Messages/pages enter a user JSON data payload under a fixed system policy. Models have no tools, credentials, policy-editing or Discord authority. Extracted quotations must occur in the original text; claim relations, source IDs, score references and response shapes are validated. Page retrieval allows HTTPS public addresses only, checks all DNS results, connects to the validated address with hostname-verified TLS, revalidates redirects, refuses credential-bearing provider redirects, and bounds response size/time. Script/style/navigation text is discarded. Evidence remains untrusted and can be disputed; automated analysis is labelled separately from staff actions.

API contracts: [official OpenAI Chat Completions documentation](https://developers.openai.com/api/reference/resources/chat/subresources/completions/methods/create) and [Brave Web Search documentation](https://api-dashboard.search.brave.com/app/documentation/web-search/codes).

## Judging and competition

Arena-v1 scores 0–100 on reasoning (25%), evidence (20%), assessed factual accuracy (15%), engagement (20%), clarity (10%) and rules (10%). The accepted weights must be nonnegative integers totalling 100. Accuracy is omitted and remaining weights renormalized when the participant has no assessed factual evidence; values are evaluated through reasoning and justification. Scores require real transcript/claim references. A difference of at most three points is a draw by default; the agreed tie policy may instead be inconclusive. An insufficient basis is always inconclusive. Reports expose dimension scores, totals, weights, references and actionable feedback. Live scores, audience opinion, factual verdicts and procedural outcomes remain distinct.

Ranked-v1 fixes the default rubric/weights/model/tie policy, message turns, first speaker 0, 24-hour response window, coaching/live scores off, and 10 rounds/100 messages/4,000 characters. Other optional assistance is symmetric and visible. Disabled judging makes a match casual. Initial Elo is **1000**, **K=32**; operators may configure both for future accepted matches. Elo uses expected score `1 / (1 + 10 ** ((opponent - self) / 400))` and update `K * (actual - expected)`. Wins/concessions/forfeits score 1/0; draws score 0.5. Cancellations, inconclusive/review-pending results, casual play and training do not affect Elo.

Both members must complete at least one official turn before a result is eligible. At most three ranked results against the same opponent per UTC day affect ratings; this policy is snapshotted at acceptance. Every outcome remains in `/match history`, including casual records, topic/position context, procedural win/loss/draw/forfeit statistics and result links. This public record is separate from optional generated profile analysis. Results replay chronologically by completion time and match ID after corrections, updating later deltas and recording reversal reasons. Leaderboard filters select records by topic, period, format and minimum activity; the displayed rating remains the current lifetime rating, rather than a recalculated filtered Elo. Result links and win/loss/draw/forfeit counts accompany standings.

## Training and profiles

`/train start` supports `spot`, `selected`, `mixed`, `battle`, `repair` and `sound`; difficulty is 1–3 and topic is configurable. `/train fallacy` chooses a name/alias. Original curriculum exercises cover the README's eight families plus red herring and appeal to popularity, with variants and per-entry links crediting Bo Bennett's [Logically Fallacious](https://www.logicallyfallacious.com/fallacies). No site prose/examples are bulk copied. Mixed drills rotate categories; after sufficient practice, weak recent categories and consented match recommendations guide selection. Sound drills alternate valid and fallacious examples. Battles last three graded turns, using deliberately flawed original bot responses; if dynamic generation fails after a graded answer, the next turn uses an original curriculum example with an explicit fallback state.

Answers are free-text explanations, quotes or repairs. The LLM grades identification and explanation separately, accepts defensible overlapping labels, and explains improvements with the original teaching notes and reference link. Score is 30% identification and 70% reasoning explanation. Hints are optional and counted separately. Progress stores attempts, accuracy, recent scores, hints, per-family needs and suggested difficulty. Unavailable grading retains the answer and honest pending/failed state for retry; it does not award an invented score. Training never changes competitive records or establishes personal beliefs.

Profiles default to **analysis off, private visibility, training inclusion off**. `/profile settings` controls these plus recommendations. Both match consent and user consent are required; opt-in covers matches created after the opt-in time. Observations include topic tags, assigned positions, factual/value/conceptual themes, approach tags (evidence/examples/definitions/principles/consequences), strengths, practice needs and chronological scores, each with match/claim/message evidence and sample counts. Aggregated tendencies require three opted-in matches; earlier records show individual observations without a permanent label. Topic interests describe managed debate activity, not inferred beliefs or diagnoses. Unrelated server conversation is never analyzed for profiles.

Visibility applies at read time, including staff viewing another user's profile. Users can annotate a correction or exclude an observation; exclusions survive regeneration. Disabling analysis stops future generation. `/profile remove-insights` deletes generated observations, disables analysis and records a removal cutoff so old jobs/reviews cannot recreate them. Re-enabling covers future matches only. Public debate transcripts, result/audit records and training attempts remain their separate records. Opted-in training adds recent practice history; practice recommendations link back to eligible reasoning evidence.
